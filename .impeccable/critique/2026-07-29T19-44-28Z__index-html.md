## Design Specificity Verdict

**LLM assessment**: Authored for the product, not category-interchangeable. The Command Deck palette, the per-unit hero-image overlay with round/VP chip, the flat stat row, the fanned tactics-hand widget, and the twist-card "briefing" panel (with real Warhammer-house-style copy) all show specific intent toward "companion app used at a table during a live game," not a generic dark card-tracker. The weak spot is that the specificity is mostly *visual* — the *interaction* model (tap targets, feedback, error recovery) is closer to a generic form-heavy admin panel than a tool built for one-handed, high-stakes, repeated use mid-match.

**Deterministic scan** (`detect.mjs`, exit code 2, 16 findings — all `warning`, 0 `error`):
- **overused-font** ×14 — every `font-family: 'Inter'` declaration plus the Google Fonts import. Likely a detector reflex against a very common default font rather than a real problem here: Inter is deliberately paired with Oswald as a two-font system (headers/labels vs. body), not an unconsidered default. Flagging it 14 times (once per declaration) inflates the count; treat as one finding, not fourteen.
- **layout-transition** ×1 (line 991) — `transition: width` on the HP bar fill. Real but minor: animating `width` forces layout on every HP change; `transform: scaleX()` would be cheaper. Low priority given the element is small and changes are infrequent.
- **em-dash-overuse** ×1 (advisory, file-level) — 11 em-dashes in body copy. Stylistic, not a defect.
- **dark-glow** ×1 (line 208) — a zero-offset `text-shadow` glow at `rgba(158,120,56,.30)` on `.hero h1`. **This selector is dead code** — the header now renders the official GW logo as an `<img class="hero-logo">`, not an `<h1>`, so this rule (and its sibling `filter: drop-shadow(...)` two lines above) never matches anything. Leftover from before the logo swap; should be deleted, not just muted.

**Visual overlays**: no live-injection overlay was run this pass (Assessment B used direct browser inspection and JS sampling instead of the detector's page-injection script); findings above come from the CLI scan plus manual DOM/contrast sampling, not an in-page overlay.

## Overall Impression

The visual identity is genuinely committed and well-matched to the product — this doesn't read as a template. But the interaction layer hasn't caught up to the visual layer: the single most-repeated action in a real game (adjusting HP) has no visual escalation, no touch-differentiated colors, and no undo, and the persistent game state (round/VP) vanishes on two of the four tabs. The biggest opportunity is closing that gap — the "brains" of a scorekeeping tool (state visibility, error recovery, fast repeated input) matters more here than any further visual polish.

## What's Working

- **Twist-card briefing panel** — full-bleed dark gradient, italic tag, capitalized title; it reads like a real event card being revealed, not a modal dumping text. This is the strongest emotional beat in the app and it's specific to this product's "twist deck" mechanic.
- **Native `<details>` accordions for weapons/abilities/lore** — keeps a lot of dense rules text one tap away instead of off-screen or cluttering the card, which matters for a tool that gets referenced dozens of times per game.
- **Per-unit hero image with overlaid stat/round chip** — reduces context-switching by putting a unit's art, name, and current game context in one glanceable block (when that chip is actually reachable — see Priority Issues #1).

## Priority Issues

**[P0] Damage and heal buttons are visually identical at rest.** Both `.hpbtn.dmg` and `.hpbtn.heal` only diverge in color on `:hover`, a state that never fires on a touchscreen. On the actual device used at the table, "−" and "+" are two identical grey circles distinguished only by their glyph. In a stressful moment (opponent just rolled damage, player is tracking multiple things at once), mis-tapping the wrong one silently corrupts the HP count with no undo. **Fix**: give `.hpbtn.dmg`/`.hpbtn.heal` distinct resting-state colors (e.g. ember/red-leaning for damage, the existing dolorum-green for heal) instead of hover-only differentiation. **Suggested command**: `/impeccable colorize` (or `/impeccable harden`, since this is really an error-prevention gap).

**[P1] Round/VP state disappears on the Твист and Тактики tabs.** The chip only renders inside the Подготовка control panel and repeated on each unit's herotopbar (Армия tab) — there is no equivalent on Твист or Тактики. A player resolving a twist card or picking a tactic loses sight of the round number and score, both of which matter to the decision they're making right there. **Fix**: render the same `data-roundchip`/`data-vpchip` pair (already broadcast by `refreshHeroChips()`) into a compact strip at the top of the Твист and Тактики tab panels too — the plumbing already exists, it's a placement gap, not a new system. **Suggested command**: `/impeccable layout`.

**[P1] No undo/recovery for HP, VP, or discard-and-draw.** Toasts are purely informational (`toast('...')` with no action). A misclick has no path back except manually recomputing the correct number under time pressure. **Fix**: make the toast for HP/VP changes actionable with a 4-5s "Отменить" affordance that reverts the last delta. **Suggested command**: `/impeccable harden`.

**[P2] HP bar communicates only by length, never by color.** `.hpbar .fill` stays the same steel-grey (`--danger`/`--steel`) whether a unit is at 6/6 or 1/6. For a game about attrition, "this model is about to die" is exactly the moment that deserves a visual escalation. **Fix**: shift the fill hue as the ratio drops (steel → amber → red), matching the ember-red palette already in use elsewhere for alerts. **Suggested command**: `/impeccable colorize`.

**[P2] Dev-only "Выгрузить armies.json" export sits inline with primary army-selection controls, same pill-button weight as everything around it.** It's a debug/backup tool, not a player-facing in-session action, but nothing visually marks it as secondary. **Fix**: move it out of the primary flow (a settings/footer area) or demote it to a smaller ghost-style link. **Suggested command**: `/impeccable layout`.

## Persona Red Flags

**Alex (plays every week, wants speed and muscle memory)**: Every HP change is a full-size button tap, repeated dozens of times a game, with zero shortcuts or gesture support (swipe-to-damage, long-press-to-set). Losing round/VP visibility on two tabs also breaks the "glance and go" flow Alex relies on.

**Jordan (first game ever, needs the UI to teach as it goes)**: Phase icon-tiles (Move/Shoot/Charge/Combat) give no indication they're tappable until after the first tap reveals the "on" state — a first-timer won't know what they do. Rules jargon (Rend, Strike-first, Ward) is tooltip-linked inside weapon tables only; the identical jargon in twist-card and tactic-card body text is plain, unlinked text.

**Sam (one hand free, holding dice/rulebook)**: `.hpbtn` (28×28), `.term-clickable` tooltip triggers (as small as 63×13), and the `.tiny.primary` ability-used buttons (157×34) all sit under the ~44px touch-target floor the product's own PRODUCT.md sets as a legibility/usability requirement for one-handed, dim-room use.

## Minor Observations

- Dead CSS: `.hero h1` (line ~203, including its `text-shadow`/`drop-shadow` glow) targets a heading that no longer exists in the markup — the header renders the GW logo image now. Safe to delete.
- `transition: width` on the HP bar fill (line 991) forces layout on every change; `transform: scaleX()` on a fixed-width track would be cheaper, though the practical cost here is small.
- Weapon names wrap mid-word on narrow phones ("Daemo­nflame Glaive"), which the browser check found readable but tight at 375px.
- Locked "Скоро" mode posters give zero hint of what's coming — even a one-line teaser would turn dead space into anticipation.
- The detector's 14 separate `overused-font` hits are really one finding (Inter used file-wide) counted per-declaration — worth noting so it isn't mistaken for 14 distinct problems.

## Questions to Consider

- If round/VP is state every screen needs, why does it only reach two of four tabs when the broadcast mechanism (`refreshHeroChips`) already updates every instance on the page?
- Should HP ever be silent (grey, static) in a game whose emotional core is "how much punishment can this unit take before it dies"?
- Is the raw JSON export really a day-one, in-session control — or backlog/debug tooling that's been wearing the same pill button as "Draw a card" since early development?
